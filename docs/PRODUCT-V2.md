# 麦麦账本 V2 · 从「审计报告」到「点单代理人」

> 状态：产品设想稿 · 用于内部讨论
> 前置事实全部来自本机真实 MCP 调用（2026-10-20 13:19–13:21，真实账号 + 真实门店 1420670），非纸面推演。标注「未实测」的部分会明确写出。

---

## 0. 一句话结论

**现在这份账本回答的是「我过去花得对不对」，而用户真正想知道的是「我现在该怎么点」。**
两者之间差的不是数据，也不是可视化，而是一个**决策闭环**：把「历史画像 + 实时账户 + 当下意图」压缩成一个可直接执行的方案，并且让执行这一步只需要一次点击。

账本已有的全部工作没有白做——它是这个闭环的**先验**。没有「你过去 21 笔早餐有 15 笔没用券」这个事实，任何比价工具给的建议都是通用的，用户不会为通用建议改动自己的习惯。

---

## 1. 现状诊断：为什么"汇总展示"价值有限

| 现状 | 用户拿到的东西 | 用户还差的一步 |
|---|---|---|
| 三层价拆解 | 知道你被套餐赚了多少 | 下次点单时想不起来 |
| 归因 | 知道 ¥247 是券省的、¥61 是漏的 | 漏掉的那 ¥61 已经花了 |
| 策略建议（本轮已做） | 「早餐 21 笔里有 15 笔没用券」 | 明天早上还是照旧点 |
| 画像 | 知道自己是"早餐型、爱套餐" | 知道之后没有任何变化 |

**核心问题：所有产出都停在"认知"层，没有进入"动作"层。**
用户看报告的那 3 分钟，和真正点单的那 3 分钟，是两个完全不同的时刻。报告的价值在 3 分钟后衰减到接近 0。

一个可以自测的判据：**如果用户做完了这份报告里建议的事，他会不会回来再看一遍？** 现在的答案是"不会"，因为下次点单时报告不在场。

---

## 2. 核心洞察：决策的三要素

用户点单时的决策成本可以拆成三段，每一段都能被账本吃掉：

```
① 选什么   ← 决策疲劳（每天中午重新想一遍吃什么）
② 怎么买   ← 信息不对称（同一个汉堡有 5 种买法，菜单只展示 1 种）
③ 别忘了   ← 时间约束（券有窗口、活动有日期、第二份半价要买 2 个）
```

现在的账本只覆盖 ②的后半段（事后归因），①③完全空白。而 ①③ 恰恰是**可以自动化**的部分——因为它们不需要用户表达偏好，只需要用户说一句"老样子"。

### 2.1 五个真实动机（按出现频率）

1. **「我就想吃这个，但别让我买贵了」** —— 最高频。已经有明确目标商品，只需要一个最优买法。
2. **「每天中午都不知道吃什么」** —— 决策疲劳。需要的是"替我决定"，不是"给我更多选项"。
3. **「券又在卡包里躺到过期」** —— 损失厌恶。券是已经到手的钱，废掉的心理痛感远大于"没领到"。
4. **「这个卡到底值不值」** —— 订阅焦虑。¥19/月的卡，用户自己算不清，因为需要的正是历史频次。
5. **「帮同事一起点，怎么分摊最省」** —— 低频但强需求，发生在办公室场景。

前 3 个覆盖了绝大部分日常点单次数。第 4 个虽然频率低，但涉及**周期性付费**，决策权重极高。

### 2.2 一个关键判断

> **决策引擎的输入不是"用户想要什么"，而是"用户接下来大概率会做什么"。**

账本已经能预测这件事（早餐 7:27–7:46、午餐 12 点前后、33 笔/月、常点「人气经典随心配」、早餐券使用率 29%）。所以正确的产品形态不是"让用户描述需求"，而是**"我猜你要这个，方案已经算好了，只要点一下"**。

这也是它和市面上比价工具的根本区别：**别人从菜单出发，我们从你的历史出发。**

## 3. 场景设计

每个场景按「动机 → 触发 → 决策 → 输出 → 价值」描述。输出形态都写成了用户真正看到的那一屏。

### 场景 A · 一键复购：老样子，但更便宜

- **动机**：决策疲劳。中午 12 点，不想选。
- **触发**：进入页面 / 到常用点单时段（账本已知你的午餐时间是 11:50–12:30）。
- **决策**：从账本取该时段 Top 3 高频组合 → 用**当前**菜单价 + **当前**券重算 → 输出"最便宜的等价替代"。不是简单重复历史订单，而是把历史意愿用今天的价格重新解一次。
- **输出**：

  ```
  【今天的午餐 · 照旧】
  麦辣鸡腿堡 + 可乐                ¥11.90 + ¥9.50 = ¥21.40
  用券「11.9元麦辣鸡腿堡」，券 10-23 前有效     [ 就这个，去取餐 ]
  ────────────────────────────────────────
  你过去 30 天在这个时段点了 12 次，
  其中 9 次没用券，平均每笔多花 ¥11.10。
  ```

- **价值**：把"选什么"的决策时间从 ~90 秒压到 0；把"怎么买"从默认价改到券价。按账本数据，早餐场景月化空间 ¥94.50，午餐同类空间相当。
- **依赖**：`query-meals`（常点 `frequent` 字段已验证返回）+ `query-store-coupons` + `calculate-price`。

### 场景 B · 实时比价：我想吃这个，别让我买贵

- **动机**：目标明确，信息不对称。
- **触发**：用户点任意商品（或语音/文字说"巨无霸"）。
- **决策**：对同一目标枚举 5 条买法，**每条都走一次真实结算**，按实付排序：
  1. 单点 + 可用券
  2. 套餐（含更多东西，需标注增量）
  3. 随心配 1+1 组合
  4. 随单购卡（卡钱计入总价）
  5. 拆成 2 件单点（利用第二份优惠/低价单品）
- **输出**（真实数据构造）：

  ```
  【麦辣鸡腿堡 · 4 种买法】

  ① 用券单点                    ¥11.90   省 ¥11.10
     券「11.9元麦辣鸡腿堡」· 到店自取
  ② 麦辣鸡腿堡三件套             ¥34.00   省 ¥13.50
     比 ① 贵 ¥22.10，多薯条 + 可乐
  ③ 随心配 1+1                  ¥14.90
     不含麦辣鸡腿堡，需换品
  ④ 裸买                        ¥23.00

  ⚠ 菜单上显示 ¥11.9 的那个价，需绑定「随单购」才能享受；
    不绑定时的实付是 ¥23.00。
  ```

- **价值**：这是**单次收益最高**的场景。实测同一商品从 ¥23.00 到 ¥11.90，差价 48%。
- **关键**：必须用 `calculate-price` 的**结算价**，不能用菜单 `currentPrice`。原因见 §5.2 的实测证据。

### 场景 C · 过期挽回：券要废了，我提前帮你下好

- **动机**：损失厌恶。券是已到手的钱。
- **触发**：券到期前 T-24h 与 T-2h 两级。
- **决策**：判断"用户在该券有效窗口内是否大概率会下单"——用账本的历史时段分布判断，不是无脑提醒。用户早餐固定在 07:27–07:46，而券要求 05:00–10:29，命中概率高，就值得提醒；如果用户从不吃早餐，提醒就是骚扰。
- **输出**：

  ```
  【明天 10:29 过期】高达芝士蛋堡早餐两件套 ¥9.90
  你通常 07:30 下单，还剩 19 小时。
  [ 明早 07:40 帮我下好 ]  [ 不要了 ]
  ```

- **价值**：一张早餐券面值约 ¥14（原价 ¥24 − 券价 ¥9.9）。账本当前 3 张券，全部挽回 ≈ ¥40。按券的生命周期，一个月约 8–10 张 → **月挽回 ¥100 量级**，与策略引擎算出的 ¥94.50/月 高度吻合（两条独立路径互相印证）。
- **依赖**：`reservationDate` 预约单（`calculate-price` 与 `create-order` 均支持，格式 `yyyy-MM-dd HH:mm`）。

### 场景 D · 订阅回本：这张卡到底值不值

- **动机**：周期性付费焦虑。麦金卡月卡 ¥19。
- **触发**：卡到期前 7 天；或用户首次遇到"随单购优惠"价签时。
- **决策**：`净收益 = 历史 30 天频次 × 卡内价差 − 卡价`，并给出回本点：

  ```
  【麦金卡 ¥19/月 · 你还差 1 次回本】
  过去 30 天你买了 33 笔，其中 21 笔符合麦金卡优惠。
  每笔平均节省 ¥1.80 → 月省 ¥37.80，净赚 ¥18.80。
  如果你下个月只买 11 笔，就不划算了（回本线 11 笔）。
  [ 保持续费 ]  [ 到期提醒我 ]
  ```

- **价值**：这是**用户自己算不清**的决策，且金额明确（¥19/月 × 12 = ¥228/年）。同时它反向验证场景 B——不买卡时算出的"裸买价"才是真实基准。
- **依赖**：纯本地计算（账本数据 + 菜单价差），**零额外 MCP 调用**，成本极低。

### 场景 E · 凑单补齐：差 4 块才到门槛

- **动机**：券有门槛，用户不知道该不该加。
- **触发**：`calculate-price` 返回 `enjoyable.balance`（门槛差额）非 0 时自动出现。
- **决策**：加一件**最便宜且不破坏原优惠**的商品，算净收益。净收益 = 券优惠 − 加购成本，必须为正才推荐。
- **输出**：

  ```
  【还差 ¥4.00 可用「满 30 减 10」】
  加 圆筒冰淇淋 ¥5.00 → 总价 ¥31.00，券后 ¥21.00
  比现在（¥26.00 不用券）还便宜 ¥5.00，且多一个冰淇淋。  [ 加上 ]
  ```

- **价值**：API 直接给差额字段，**实现成本近乎为零**，但每次能多省 ¥5–15。这是典型的高杠杆功能。
- **注意**：必须做"净收益为正"的硬校验，否则会变成"劝你多花钱"的反向体验。

### 场景 F · 拼单分摊：帮同事一起点（低优先）

- **动机**：办公室场景，一次 5–8 人。
- **决策**：多人意图合并 → 券只有一张时，比较"用券给总额"vs"给最贵单品"哪个总成本低 → 拆单或合单。
- **关键约束**：实测**一单只能用一张券**（见 §5.2），所以多人拼单的核心问题恰恰是"哪些人合单、哪些人拆单"。
- **价值**：单次金额大（¥100+），但频率低、需要多人协作入口。放 P2。

## 4. 执行授权阶梯：自动到什么程度

这是整个 V2 最需要产品拍板的地方。技术能力上可以一路做到"代付"，但**信任必须是渐进的**。

| 级别 | 名称 | 系统做什么 | 用户做什么 | 风险 | 本期 |
|---|---|---|---|---|---|
| **L0** | 只读展示 | 出报告 | 自己点 | 无 | 已完成 |
| **L1** | 建议 | 算出方案，给一句话 + 差价 | 自己照着点 | 无 | **P0** |
| **L2** | 预填 | 生成待支付订单（含商品/券/取餐方式） | 确认 → 扫码支付 | 低（未支付可撤） | **P1** |
| **L3** | 预约 | 授权后，按约定时间自动生成**预约单** | 到点去取，现场支付 | 中（时间错配） | P2 |
| **L4** | 代付 | 自动下单 + 自动支付 | 什么都不做 | 高（资金） | 不做 |

### 4.1 一个必须说清的能力边界

**MCP 没有「购物车」这个概念。** 32 个工具里与下单相关的只有 `create-order`——它直接生成**待支付订单**并返回支付链接，没有"先加购物车、稍后调整"的中间态。

所以「一键加入购物车」这个设想，在现有 API 下的准确形态是：

> **一键生成「待支付订单」+ 一键撤销。**

这意味着 L2 的实现必须自带两个护栏：
1. **幂等键**：同一意图 10 分钟内只允许生成一单，防连点。
2. **可撤销**：`cancel-order` 必须可用（未实测，需在接入时首要验证）。
3. **明确文案**：按钮写「生成待支付订单」，不写「加入购物车」——不能给用户错误的心理模型。

### 4.2 默认授权（已拍板：L2）

**决策：默认停在 L2。** 即系统直接生成「待支付订单」，用户确认后扫码支付。

这意味着 L2 的三条护栏从"可选"变成"必需"，缺一不可：

| 护栏 | 具体做法 | 缺了会怎样 |
|---|---|---|
| **二次确认** | 生成前展示一屏确认卡：商品明细 / 用哪张券 / 单数 / 取餐方式 / 实付金额 | 用户点错就直接产生待支付单 |
| **幂等键** | 同一意图（门店 + 商品指纹 + 券 + 10 分钟窗口）只允许生成一单 | 连点两下 = 两张待支付单 |
| **一键撤销** | 待支付页常驻「撤销」按钮，调 `cancel-order` | 用户被一张不想要的单卡住，信任崩塌 |

补充两条硬约束：

- **金额上限**：单笔 > ¥100 时降级回 L1（只建议），必须在设置里可改。
- **文案**：全链路禁用「已下单 / 购买成功 / 已支付」，只能出现「待支付」。用户没付钱就不能说买了。

自动预约仍留在 **L3 且逐次确认**，不做常驻授权——因为 L2 的"错"是几分钟内可撤销的，L3 的"错"是第二天早上你人不在那个门店。

## 5. 技术地基（全部实测）

这一节是文档最硬的部分。以下每条都是本机真实调用结果，不是推断。

### 5.1 已验证的能力矩阵

| 能力 | 工具 | 状态 | 实测结论 |
|---|---|---|---|
| 查可售商品 + 价格 + 常点 | `query-meals` | ✅ 实测 | 返回 90+ 商品、19 个分类、`frequent` 常点字段 |
| 查**我的**券（含 id/code） | `query-store-coupons` | ✅ 实测 | 返回 `couponId` / `couponCode` / 绑定 `productCode` / 有效期 |
| 精确结算（含券） | `calculate-price` | ✅ 实测 | ¥23.00 → **¥11.90**，券生效 |
| 精确结算（含随单购卡） | `calculate-price` + `withOrder` | ✅ 实测 | ¥66.50 → **¥56.00**（商品 ¥37 + 麦金卡 ¥19） |
| 一键领全部可领券 | `auto-bind-coupons` | ⚠️ 未实测 | 无参数，理论上最安全的写操作 |
| 预约单 | `reservationDate` 参数 | ⚠️ 未实测 | 两接口均声明支持 |
| 创建订单 → 支付链接 | `create-order` | ✅ **实测** | ¥5.00 圆筒，返回 `orderId` / `payId` / **`payH5Url`** / `expirePayTime`（+15 分钟） |
| 撤销订单 | `cancel-order` | ✅ **实测** | `cancelResult: true`，复查 `orderStatus = 订单已取消` |

**完整闭环已跑通**（2026-10-20 13:43，真实账号 / 门店 1420670，¥5.00）：

```
calculate-price(515837 ×1)        → ¥5.00，takeWayList: eat-in / take-in-store
create-order(takeWayCode=take-in-store)
  → orderId  1030291570000661981053416218
  → payH5Url https://m.mcd.cn/mcp/scanToPay?orderId=1030291570000661981053416218
  → expirePayTime 2026-10-20 13:58:49   （下单后 15 分钟）
cancel-order(cancelReasonCode=3)  → cancelResult: true
query-order                       → orderStatus: 订单已取消
```

**这是 L2 可行的决定性证据**：生成待支付单 → 拿到支付链接 → 撤销 → 状态归零，全程 11 秒，无残留。

一个重要的接口细节：`query-my-coupons` 和 `available-coupons` **只返回 markdown 文本，没有 `couponId`**；只有 `query-store-coupons` 返回含 id 的结构化 JSON。所以「自动用券」必须走后者，前者只能用于"有哪些券"的展示。（本项确认过一次：两个接口的返回中均无 id 字段。）

### 5.2 五个真实约束（决定了产品能做到什么）

**① 一单只能用一张券。**

实测两张券同单，返回 `code 600022 · 暂不支持多张券使用`。

后果：这不是"组合优化"问题，而是**"选哪张 + 要不要拆单"**问题。拆单是有代价的（多跑一趟、多个取餐码、外送时配送费重复），所以最优解是四元组联合优化：
`(券选择, 商品组合, 单数, 取餐方式)`。
这一条反而是机会：**没人帮用户算过"2 张 ¥9.9 早餐券，分两单还是一次用完"**。

**② 菜单价 ≠ 结算价（最容易被误读的一条）。**

实测「安格斯厚牛堡四件套随心选」：菜单 `currentPrice` = **¥37.00**，但直接结算（不传 `withOrder`）实付 **¥66.50**。
¥37 是"随单购麦金卡优惠"价——必须先买 ¥19 的麦金卡。传 `withOrder` 后结算返回的商品列表里会**显式出现**「麦金卡月卡（30天）¥19.00」，总价 ¥56.00 完全透明。

后果：任何"从菜单价直接算差价"的做法都会给出错误建议。**决策引擎必须调用 `calculate-price` 拿真实结算价，这是不可省略的一步。**

**③ 菜单标签不保证在结算时生效。**

实测「圆筒冰淇淋」标着"第二份半价"，买 2 个结算 **¥10.00（无折扣）**。
后果：不能用 `tags` 做价格推理，标签只能当"值得去试"的线索。

**④ 商品随时段和库存失效。**

实测「优品豆浆 ¥10」上午 10:15 可售，同一天 13:19 结算报 `60006 商品已售罄或不可售`。
后果：方案必须在**执行前一刻**重新校验，不能缓存超过分钟级。这直接决定了系统架构——见 §5.3。

**⑤ 取餐方式是下单的必传字段。**

`create-order` 要求 `takeWayCode`，取值来自 `calculate-price` 返回的 `takeWayList[].code`（实测当前门店返回 `eat-in` 堂食 / `take-in-store` 外带）。
后果：**结算与下单必须是同一个方案对象**，不能分两次独立构造。这是把"方案"做成一个不可变对象的技术理由。

**⑥ 支付凭证是 H5 链接，不是二维码图片。**

`create-order` 返回 `payH5Url = https://m.mcd.cn/mcp/scanToPay?orderId=<orderId>`，没有任何图片字段。
后果：待支付页的二维码要**自己在客户端把这个 URL 编码成 QR**（推荐，不依赖 WebView 权限，用户还能用另一台设备扫）；或者内嵌 WebView 打开。
⚠️ 这个链接带 `orderId`，属于一次性凭证——**不能进日志、不能进截图、不能写进分享卡**。

**⑦ 待支付单 15 分钟后自动过期。**

实测 `expirePayTime = 下单时间 + 15 分钟`。
后果：倒计时上限就是 15 分钟，界面直接照这个数写。过期后必须能「重新生成」——重新走 `calculate-price → create-order`（因为价格和库存可能已变），而不是让用户对着一个死链发呆。

**⑧ `status` 的实际取值与官方文档不一致（会写出永远不触发的判断）。**

| 状态 | 文档声称 | 实测 |
|---|---|---|
| 待支付 | `1` | **`10`** |
| 已取消 | `7` | **`60`** |

后果：**订单状态一律用 `orderStatus` 文本判断**（`"待支付"` / `"订单已取消"`），不要用 `status` 数字。
如果照文档写 `if (status === 2) 已支付`，轮询永远不命中——用户钱付了，页面还停在"待支付"。这是最伤信任的一类 bug。

**⑨ 未支付时没有取餐码。**

实测 `pickupCode` 为空串，支付完成后才生成。
后果：拆单场景（决策 2）必须等**两单都支付成功**才拿得到两个取餐码。待支付页不能提前展示取餐码，也不能承诺"两单同时出码"——两单是两次独立支付。

### 5.3 架构：三个角色

```
                ┌──────────────────────┐
   历史事实 ───▶ │  Ledger（账本）      │  已有：逐单事实表 + 归因
                │  = 决策的先验        │  回答「你大概率会做什么」
                └──────────┬───────────┘
                           │ 意图 + 先验
                ┌──────────▼───────────┐
   实时账户 ───▶ │  Planner（求解器）    │  新增：方案枚举 + 结算 + 排序
   意图输入      │  = 决策的求解        │  回答「怎么买最划算」
                └──────────┬───────────┘
                           │ 方案对象（不可变）
                ┌──────────▼───────────┐
                │  Executor（执行器）   │  新增：护栏 + 幂等 + 撤销
                │  = 决策的落地        │  回答「现在做，还是等一下」
                └──────────┬───────────┘
                           │
                        MCP 写操作
```

关键设计：**方案是一个不可变对象**，包含 `items[] + couponId + takeWayCode + 结算价 + 结算时刻`。从结算到下单，传的是同一个对象，不在中途重新拼参数——这既满足约束 ⑤，也让"用户看到的价"和"实际下单的价"一定一致。

### 5.4 方案枚举的规模（可行性关键）

朴素枚举会爆炸（90 商品 × 5 买法 × N 张券）。实际的搜索空间比想象中小得多，原因有三：

- 券**绑定具体商品**（实测券「11.9元麦辣鸡腿堡」= `productCode 1440`），所以"券 × 商品"是一对一映射，不是笛卡尔积。
- 一单一张券（约束 ①），所以每单的券选择是「无券 + 3 张券」= 4 条分支。
- 目标商品通常 1–3 个，买法 5 种 → 单次决策约 **4 × 5 × 3 ≈ 60 次结算**。

60 次 `calculate-price` 显然不能串行给用户等。所以需要：
1. **两阶段**：先用本地菜单价粗筛（保留 Top 8），只对候选做真实结算。
2. **并发 + 缓存**：同 `(storeCode, items 指纹, couponId)` 5 分钟内复用。
3. **流式返回**：先出"用券单点"这个最快最常赢的方案，其余异步补齐。

### 6.1 单次场景的实测收益

| 场景 | 实测/推算收益 | 依据 |
|---|---|---|
| B 比价 | **¥11.10 / 单**（48%） | 麦辣鸡腿堡 ¥23.00 → ¥11.90，真实结算 |
| B 比价（卡路径） | **¥10.50 / 单**（16%） | 安格斯四件套 ¥66.50 → ¥56.00（含 ¥19 卡） |
| C 过期挽回 | **≈¥14 / 张** | 早餐券原价 ¥24 − 券价 ¥9.90 |

| E 凑单 | **¥5–15 / 次** | 净收益 = 券额 − 加购成本 |

### 6.2 月度规模（基于真实账本数据）

账本当前 33 笔 / 30 天，实付 ¥442.35，已省 ¥247.45。

- 策略引擎估算的未兑现空间：**¥129.52 / 月**（其中券相关 ¥94.50）
- 用券面值独立反算：3 张券 × ¥14 ≈ ¥40 / 3 天 ← 与上面两条路径吻合
- **V2 可兑现比例**：假设比价场景覆盖 60% 订单、单均省 ¥8（券路径与卡路径加权）→ **约 ¥160 / 月**

也就是说：**V2 让这份账本从"告诉你少了 ¥129"变成"每月真的拿回 ¥100+"。** 这是从"信息产品"到"效果产品"的跃迁，也是用户愿意持续打开它的理由。

### 6.3 北极星指标建议

不要用"报表打开次数"（那是 L0 的指标）。建议：

> **月度实际兑现节省额** = Σ(通过本产品生成/推荐的订单，相对该商品默认买法节省的金额)

配套过程指标：
- **方案采纳率**（生成方案 → 用户执行）——衡量建议质量
- **券兑现率**（券用掉 / 券到手）——衡量场景 C 的效果
- **决策耗时**（进入页面 → 执行）——衡量场景 A 的价值

### 7.1 里程碑建议

**M1（只读，2 周）— P0 三件套**
`calculate-price` 封装 + 5 种买法枚举 + 方案卡 UI + 凑单提示 + 卡回本计算。
产出：**用户能看到"同一顿饭的 4 种买法"**。不涉及任何写操作，零风险，可独立上线。

**M2（半自动，3 周）— 场景 A + 拆单**
意图模板（"老样子"/"想吃 X"）+ 先验排序 + 拆单比价。
产出：**从"给我选项"变成"这是你的方案"**。

**M3（可执行，需授权设计）— 场景 C**
调度器（T-24h / T-2h）+ 授权流 + `create-order` + `cancel-order` + 幂等/金额上限护栏。
产出：**券不再过期**。这一步才真正触碰写操作，必须先完成撤销验证。

## 8. 风险与边界

| 风险 | 后果 | 对策 |
|---|---|---|
| **误下单** | 真实资金损失 + 用户信任崩塌 | 默认 L1；L2 需显式点击；幂等键；单笔金额上限（建议 ¥100）；`cancel-order` 必须验证可用 |
| **价格承诺** | 展示 ¥11.90，下单变 ¥23 | 方案对象不可变（§5.3）；下单前用同一对象重算；价差 > ¥0.5 时中断并要求确认 |
| **售罄/时段切换** | 方案失效（实测已出现） | 执行前强制重校验；失败时给"最接近的替代"而不是报错 |
| **券库存竞争** | 券被别人领走/用掉 | 结算即锁定；失败降级到无券方案并说明 |
| **推荐导致超支** | 凑单变成"劝你多花钱" | 净收益必须为正才推荐；不做"再加 ¥20 省 ¥5"这种 |
| **合规（比赛规则）** | 不得贬低品牌 | 表述用"价签与结算价的差异需绑定权益"，不做"套路/坑"这类定性；所有对比只在用户自己的历史内做，不与其他品牌比 |
| **隐私** | 消费数据敏感 | 数据不出本机；写操作前必须逐次确认 |

## 9. 已拍板的 4 个决策（2026-10-20）

四个问题已定，下面记的是**决策本身 + 它往下压出的设计约束**。这些约束对界面和实现都是硬要求。

### 决策 1 · 默认授权 = L2

系统直接生成待支付订单，用户确认后扫码支付。

**下游约束：**

- **主 CTA 改文案**：`去点单` → `生成待支付订单`。全链路不出现「已下单 / 购买成功」。
- **必须有一个"待支付"状态页**，且它是产品里最重要的一个页面：
  - 订单摘要（商品 / 券 / 单数 / 取餐方式 / 实付）
  - 支付二维码（把 `payH5Url` 本地编码成 QR，不依赖 WebView）+ 跳转 App 的入口
  - **常驻「撤销」** —— 这是 L2 的安全绳，不能藏在二级菜单里
  - 倒计时 **15 分钟**（实测 `expirePayTime`），过期后给「重新生成」而不是死链
- **生成前的一屏确认卡**是必经步骤，不能省。它同时承担"价格承诺"的作用：卡上显示多少，下单就是多少。
- **幂等 + 金额上限**（> ¥100 降级 L1）进第一版，不做"以后再补"。
- **阻塞项已解除**：`cancel-order` 实测可用（`cancelResult: true`，复查状态归零）。L2 可以接线了。

### 决策 2 · 接受拆单

利用「一单一张券」的约束多省 ¥10–20，代价是多个取餐码。

**下游约束：**

- 方案不再是一个订单，而是**一个"方案组"**：`{ 单数, orders[] }`。数据结构从 `Order` 升级为 `Plan`，这是本决策最大的实现影响。
- 界面上「1 单」和「2 单」必须**并列对比**，且拆单要显式标出代价：

  ```
  ○ 合单  1 单   ¥31.90   用 1 张券
  ● 拆单  2 单   ¥21.80   用 2 张券   省 ¥10.10 · 多 1 个取餐码
  ```

- **下单必须串行**，且每单独立可撤销——第 2 单失败时，第 1 单不能变成孤儿单。
- 外送场景要额外算**配送费是否重复**（拆单 = 两次配送费），这个数字常常直接否掉拆单方案。
- 拆单的收益阈值建议设 **≥ ¥5** 才提示，否则为了 ¥2 让用户跑两趟是负体验。

### 决策 3 · 券到期推送改为「命中率 > 70% 才推」

业界默认的 T-24h 全量推送一个月约 8–10 次，太吵。改为**按预测命中率过滤**。

**下游约束：**

- 需要新增一个**命中率模型**，这是本决策唯一的新增算法：

  ```
  命中率 = 该券有效窗口内、用户历史下单的概率
         = (历史落在该窗口内的订单数 / 该窗口天数) / 该窗口的日均点单上限
  ```

  简化实现：统计过去 60 天里，用户在券窗口时段（如 05:00–10:29、周一至五）下过单的天数占比。
  账本已经有全部原始数据，**不需要新的 MCP 调用**。

- **阈值 70%** → 预期推送从 8–10 次/月降到 **2–3 次/月**。这个下降本身是可测量的验收指标。
- 必配三个开关，否则 70% 也会翻车：
  - 每张券**只推一次**（T-24h 命中率高就推，推了就不再追）
  - **静默时段**（22:00–07:00 不推）
  - 「这类券以后别提醒我」——按品类退订，不是全局关
- 推送文案必须带**具体动作**（"明早 07:40 帮我下好"），纯提醒（"你有券要过期了"）直接砍掉——那种才叫吵。

### 决策 4 · 做买卡推荐

场景 D 从"可选"升级为 **P0**，因为它零 MCP 调用、纯本地计算，且能反哺比价场景的基准价。

**下游约束：**

- **强制双栏对比**，不能只展示买卡方案：

  ```
  不买卡   安格斯四件套                ¥66.50
  买卡     同款 ¥37.00 + 麦金卡 ¥19.00  ¥56.00   ← 省 ¥10.50
           卡在 30 天内继续用，再买 1 次即回本
  ```

- **必须给回本线**，而不是只给结论：「你还差 1 次回本」「下个月买满 11 笔才划算」。这是唯一能让用户自己判断的依据。
- **合规措辞**：产品定位是"算清盈亏平衡点"，不是"推荐你买卡"。标题用「这张卡值不值」，不用「开通更省钱」。不做默认勾选、不做倒计时催促。
- 与决策 1 的联动：买卡方案的按钮也只能是「生成待支付订单」，卡和商品在**同一张单**里（实测 `withOrder` 会自动把卡加进商品列表，价格完全透明）。

### 决策对优先级的改动

| 场景 | 原优先级 | 现优先级 | 变化原因 |
|---|---|---|---|
| D 订阅回本 | P0 | **P0（确认）** | 决策 4 要做，且成本最低 |
| 拆单优化 | P1 | **P1（确认，含阈值）** | 决策 2 接受，需 ≥¥5 收益才提示 |
| C 过期挽回 | P1 | **P1（加前置）** | 决策 3 要求先做命中率模型，否则不上线 |
| B 实时比价 | P0 | **P0（升级为 L2）** | 决策 1 让它可以一步到底，价值上升 |

> 注：决策 1 把 B 从"只读建议"变成"可执行"，所以 **M1 的范围需要重估**——原计划 M1 只做只读，现在 M1 至少要包含"方案卡 + 待支付确认页"的静态形态，真实下单仍在 M3。
